# Страница объекта и подбор арендаторов

Реализация пункта 6 плана и общего входа к пунктам 4–5. Для демонстрации нужны собственник, управляющий с доступом к объекту и отдельный подтверждённый аккаунт кандидата. Посетителю для просмотра опубликованной карточки вход не нужен.

## Подготовка

Применить миграции в порядке имён, включая `20261021124144_repairs_and_contractors.sql` и `20261021163501_property_hub_and_recruitment.sql`, затем опубликовать приложение. Новые функции не появятся от одной публикации фронтенда. Для проверки: в Database → Migrations должны присутствовать обе версии, а функции `property_hub`, `public_listing`, `recruitment_overview` — в базе.

Для нового предложения использовать свободный активный объект или свободное помещение. Действующие договоры и договоры на подписании блокируют публикацию, если пересекаются с предложением по помещению и заканчиваются не раньше даты доступности. Можно указать будущую доступность после окончания действующей аренды. Для всего объекта учитываются договоры всех помещений.

## Сценарий записи

1. Открыть объект из «Объектов» либо «Команда → Открыть страницу объекта». В обзоре видны ответственный, внутреннее описание, помещения, количество обращений, ремонты и аренда. Перейти к смете или отчёту через «Ремонты и подрядчики». Заявки и заметки ведутся в рабочей области команды.
2. Собственник открывает «Публичные карточки → Создать карточку», выбирает весь объект или помещение. Вводит публичное название, расположение, описание, стоимость, депозит, площадь, доступность и имя контактного лица. Точный адрес и внутренние фотографии не копируются автоматически.
3. Сохранить черновик, снова открыть «Изменить карточку», загрузить отдельные фотографии для посетителей, сохранить. Затем «Опубликовать»: проверить предварительный просмотр и подтвердить. Одна карточка на объект/помещение; для изменения существующего предложения используется та же карточка.
4. Скопировать ссылку. Открыть в другом профиле браузера без входа: видны только выбранные публичные сведения. Неопубликованные, снятые и заполненные предложения недоступны. Изменение черновика не меняет действующую публичную версию до повторной публикации.
5. Нажать «Войти и оставить заявку». После входа происходит возврат в объявление. Кандидат вводит телефон и сообщение и подтверждает передачу контактов собственнику/управляющим. Email берётся из подтверждённого аккаунта, подменить его полем формы нельзя. Отклик сохраняется один раз; свой активный отклик можно отозвать, повторная подача по той же карточке не предусмотрена.
6. Управляющий из «Поиска арендаторов» или команды открывает страницу объекта, вкладку «Кандидаты и показы». Видит контакты, назначает показ по своему часовому поясу, пишет сообщение кандидату и отдельную внутреннюю заметку. Может добавить в короткий список либо отклонить с сообщением.
7. В кабинете кандидата открыть «Поиск арендаторов»: показ и сообщение видны, внутренняя заметка скрыта. У наблюдателя команды видны только общие количества, контакты кандидатов скрыты.
8. Собственник выбирает кандидата, задаёт даты и день оплаты. В одной транзакции создаются/связываются арендатор и **черновик** договора с ценой и депозитом из исходного отклика. Позднейшее изменение объявления не меняет условия отклика. Другие активные отклики по этой карточке закрываются с уведомлением. Повторное нажатие не создаёт второй договор.
9. Через «Открыть договоры» продолжить существующий процесс: подготовка PDF, передача на подписание, подтверждение арендатором, подписанный документ, активация и заселение. На этапе выбора кандидата начисления не создаются.
10. Если ошиблись до подготовки PDF, собственник может отменить выбор с причиной. Карточка становится снятой с публикации; старый черновик договора и запись арендатора сохраняются. Удалить неиспользованный черновик в договорах, затем явно опубликовать карточку для нового набора. После подготовки документа/передачи на подписание эта отмена недоступна.

## Границы доступа и проверки

- Объект `/objects/<id>` проверяет владельца, администратора либо актуальный доступ команды. Личная роль «Арендатор» не мешает приглашённому управляющему работать с выбранным объектом. Обычный зарегистрированный пользователь видит только публичную карточку и собственные отклики.
- Управляющий ведёт кандидатов и показы; собственник/администратор управляет публикацией и выбором кандидата. Наблюдатель не получает персональные данные кандидатов. Отзыв доступа проверяется базой при каждом чтении/действии; интерфейс скрывает прежние данные при ошибке обновления.
- Новые таблицы используют RLS и закрыты для прямого браузерного чтения/записи. Доступ идёт через ограниченные RPC. Публичный снимок формируется по явному перечню полей.
- Публичные фотографии находятся в отдельном приватном bucket `listing-photos`. Доступ посетителям выдаётся только для фотографий действующей публикации. Ссылки действуют 120 секунд, после снятия новые ссылки не выдаются; уже выданная ссылка может работать до истечения срока. Загруженные файлы не заменяются/удаляются из браузера, чтобы сохранить опубликованную историю.
- Согласование действий команды и отбора использует тот же порядок блокировок: собственник, объект, публикация, отклик; версии защищают от перезаписи устаревших данных. Выбор одновременно двух кандидатов через этот процесс сериализуется. При выборе повторно проверяются действующие договоры и ранее выбранные кандидаты, включая пересечение всего объекта и помещения.
- История подбора показывает последние 50 действий, отклики — последние 200 с отметкой ограничения. В обзоре последние 20 ремонтных работ; полная история доступна в разделе ремонтов. Отклики по закрытой карточке доступны кандидату в кабинете.
- Уведомления пока внутри приложения. Рассылка по email/Telegram относится к пункту 7. Есть публичный каталог `/catalog` с поиском, фильтрами и переходом в предложение. Можно также передать кандидату прямую ссылку. Анонимных форм сбора контактов и календаря слотов показов пока нет; время назначает управляющий.

## Локальная проверка

SQL `supabase/tests/recruitment_workflow_test.sql`: анонимный доступ, публикация, приватность, роли команды, подтверждённый email и согласие, повторный отклик, показ, внутренняя заметка, устаревшая версия, выбор и договор по исходным условиям, отсутствие начислений, снятие карточки, отмена выбора и отзыв доступа. Проверки выполнялись в изолированном PostgreSQL PGlite с адаптером pgTAP; это не полная локальная инфраструктура Supabase.

Браузерный сценарий `e2e/recruitment.spec.ts` использует тестовые ответы API и отдельные контексты собственника, управляющего, наблюдателя, кандидата и анонимного посетителя. Проверяет публикацию с фото, возврат после входа, отклик, показ, приватность заметок/контактов, создание черновика, мобильный экран и отзыв доступа. Политики базы проверяются отдельно SQL-тестом.

Supabase Advisor локально недоступен: сервис PostgreSQL на `127.0.0.1:54322` не запущен. Автоматическое применение к production и проверка реальной доставки подтверждающего email не выполнялись.
