# Демонстрация расходов и результата по объектам

Пункт 2 [плана развития](./product-roadmap.md). Раздел **«Расходы и прибыль»** доступен собственнику и администратору из меню, а также из карточки объекта. Арендатору внутренние расходы, история и чеки недоступны.

## Перед публикацией

Примените миграцию `20261020204408_property_expenses_and_profit.sql` штатным механизмом деплоя Supabase, затем опубликуйте frontend. Она добавляет таблицы `property_expenses`, `property_expense_events`, проверяемый RPC `save_property_expense` и приватный bucket `expense-receipts`. Основные миграции платежного журнала должны быть применены ранее.

Проверка существования объектов через SQL Editor:

```sql
select
  to_regclass('public.property_expenses') is not null as expenses,
  to_regclass('public.property_expense_events') is not null as history,
  to_regprocedure('public.save_property_expense(uuid,jsonb,uuid,integer,text)') is not null as save_function,
  exists(select 1 from storage.buckets where id = 'expense-receipts' and not public) as private_receipts;
```

Все четыре значения должны быть `true`. Это проверяет наличие объектов; отдельно проверьте сценарий ниже под нужными аккаунтами. Из локальной сессии новая миграция к рабочему проекту не применялась.

## Сценарий для записи

Подготовьте квартиру с арендным начислением **60 000 ₽** и частичным поступлением **40 000 ₽** в текущем месяце. Коммунальное поступление не должно увеличивать арендный доход в этом разделе.

1. В карточке квартиры откройте **«Расходы и прибыль»**. Выбран именно этот объект. Фактически получено **40 000 ₽**; план аренды — **60 000 ₽**.
2. Нажмите **«Добавить расход»**: «Ремонт крана», категория «Ремонт», план **5 000 ₽**, текущая дата, состояние «Запланирован». Сохраните. Плановый результат станет **55 000 ₽**, фактический останется **40 000 ₽**.
3. Через **«Отметить оплату»** укажите фактическую оплату **5 500,25 ₽** и дату, приложите чек PDF/JPG/PNG/WebP до 10 МБ. План останется **5 000 ₽**, результат станет **34 499,75 ₽**.
4. Через **«Исправить расход»** укажите **5 200,10 ₽** и причину «Поставщик исправил сумму в чеке». Результат станет **34 799,90 ₽**. В истории остаются первоначальный план, прежняя оплата **5 500,25 ₽** и чек старой версии.
5. Добавьте ненужный плановый расход и отмените его. Он исключится из плана, но сохранится в журнале и истории. Оплаченные записи нельзя отменить или удалить через этот раздел.
6. Выберите свободную студию без договора. Запишите расход на уборку: план **500 ₽**, оплачено **450 ₽**. Результат студии станет **−450 ₽**.
7. Выберите **«Все объекты»**: фактический результат портфеля — **34 349,90 ₽**, плановый — **54 500 ₽**. Сравнение показывает отдельный результат каждого объекта.
8. Покажите фильтры периода, категории и состояния, график по месяцам и CSV-экспорт отчёта и журнала. Категория/состояние фильтруют только журнал, а сводка охватывает все расходы выбранных объектов и периода.

Администратор может пройти тот же сценарий по объекту другого собственника. Роль проверяется в базе по `user_roles`; фактический автор и причина исправления сохраняются в истории. Обычный собственник не может переносить расход в чужой объект.

## Определения расчёта

- **План аренды** — арендные начисления с корректировками за их `period_start`. Это сформированный график, а не прогноз полной загрузки или поступлений по срокам оплаты.
- **Получено аренды** — записи журнала `rent_payments`, связанные с арендными начислениями, за месяц их `paid_at`. Частичная оплата относится к месяцу поступления, даже если начисление было за другой месяц. Даты соответствуют календарной части timestamp в журнале, как в существующей аналитике платежей.
- **План расходов** — плановые суммы неотменённых записей по плановым датам. План сохраняется при оплате; последующее исправление факта не меняет исходный бюджет.
- **Оплачено расходов** — фактические суммы записей «Оплачен» по датам оплаты. Если оплата перенесена на другой месяц, план и факт попадут в разные месяцы.
- **Плановый результат** = план аренды − план расходов. **Фактический результат** = полученная аренда − оплаченные расходы.
- Депозиты, удержания и коммунальные возмещения не включаются в доход от аренды. Коммунальные расходы собственника можно отдельно внести в журнал при необходимости.

Расчёт относится только к внесённым данным. Он не заменяет налоговый или бухгалтерский учёт. Одна запись хранит одну общую сумму фактической оплаты; раздельный журнал частичных оплат расходов, банковские переводы, автоматическое распознавание чеков и интеграции с подрядчиками в этот пункт не входят.

## Проверки и ограничения проверки

- Расчёты используют целые копейки: частичные арендные платежи, корректировки начислений, разные месяцы плана/факта, пустующий объект, отмена, повторная строка платежа, отсутствие журнала и расхождения сумм проверены unit-тестами.
- Данные читаются с пагинацией; ограничение Data API по числу строк не должно молча обрезать отчёт. При недоступности журнала или расхождении его сумм с `paid_amount` фактические доход/результат скрываются с пояснением.
- SQL/RLS, роли owner/admin/tenant/anon, конкурентные версии, причина исправления, исходный бюджет, доступ к чекам и сохранность старых документов проверены `property_expenses_workflow_test.sql` в изолированной PostgreSQL через PGlite. Использован тот же адаптер Auth/Storage/pgTAP, что для актов; это не полный Supabase/Docker. Native pgTAP и advisors остаются проверкой в CI/среде деплоя.
- Браузерный сценарий `e2e/finances.spec.ts` использует локальные перехваченные Auth/REST/Storage и не изменяет рабочий Supabase. Проверяет переход из карточки объекта, план → оплата → исправление, чек, историю, отмену, сравнение объектов, CSV, мобильную ширину, отсутствие схемы/платёжного журнала и запрет входа арендатору.
