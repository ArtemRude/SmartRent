# Проверка прототипа SmartRent

Обновлено: 29 октября 2026 года. Приёмка основного сценария опубликованного прототипа завершена.

## Результат опубликованной версии — 29 октября

После подтверждения публикации пользователем проверено новое оформление уведомлений. Созданы три отдельных подтверждённых тестовых аккаунта, один объект и доступ управляющего только к этому объекту. Использованы вымышленные контакты `example.invalid`, нулевой телефон и документы с пометкой «ACCEPTANCE TEST ONLY — NOT A CONTRACT». Реальных переводов, подписания юридического договора и внешних отправок не было.

В опубликованном браузере выполнены входы всех трёх ролей, сохранение заметки собственника, отклик арендатора, создание заявки арендатора и сметы управляющего. Проверены очистка имени кандидата, недоступная коммунальная ссылка, состояние принятого ремонта и область команды с завершённой арендой. Остальная цепочка выполнена через настоящие пользовательские JWT этих ролей, без обхода RLS служебным ключом: показ и отбор → договор → загрузка PDF и подтверждение → активация → согласованное заселение → частичная учётная оплата 100 из 1 000 → заявка → смета 200 → согласование, отчёт с фото и приёмка → один плановый неоплаченный расход → новые условия с будущей ставкой 1 100 → согласованный выезд и завершение аренды.

Результат проверен повторным чтением базы через пользовательские API, отдельно от сохранённых контрольных точек запуска:

- Договор завершён; акт заселения подтверждён, выезд подтверждён и завершён.
- Отклик принят собственником, заявка закрыта, ремонт принят; расход существует в одном экземпляре и не отмечен оплаченным.
- Частичная оплата 100 сохранена; согласование будущей ставки не переписало её. До выезда подтверждены будущие начисления по новой ставке.
- Объявление имеет статус `filled` и не доступно публичному API; тестовый объект архивирован.
- Управляющий не может выбрать арендатора или утвердить смету, арендатор не может записать поступление. Закрытые финансовые таблицы не видны управляющему; рабочая область постороннего объекта возвращает `42501`.
- У всех трёх аккаунтов нет подключения Telegram и внешних доставок. Изменения действующей аренды и реальных финансовых записей не выполнялись.

Идентификатор запуска: `9415330e-939a-4146-89b3-450133489955`. Объект: `3e959848-fb49-4062-b07e-e830beb0e887`; договор: `eb060ed1-7239-4a7a-a42c-c196034cafb5`. Они оставлены как архивная история теста. Токены, одноразовые ссылки и служебные ключи в репозитории не сохраняются.

## Найдено и исправлено на рабочем окружении

1. **Ссылки входа возвращали на localhost.** Supabase Auth имел `site_url = http://localhost:3000` и пустой список разрешённых адресов возврата. Частичным изменением конфигурации установлены `https://mysmartrent.lovable.app` и точные разрешённые возвраты `/dashboard`, `/cabinet`. Остальные настройки Auth не менялись. Обычный вход по одноразовой ссылке после исправления проверен для всех трёх ролей.
2. **Storage отклонял PDF своего арендатора.** Развёрнутая политика `lease_documents_insert_tenant_signed` внутри подзапроса использовала `tenant.name` вместо пути объекта. Миграция `20261029132039_repair_tenant_document_storage_scope.sql` явно связывает проверку со `storage.objects.name`, сохраняя прежние ограничения: свой первый каталог, свой договор, статус `pending_signature`. Миграция уже применена; повторная загрузка, подтверждение и активация тестового договора прошли.
3. **Старый SQL-тест фотографий сравнивал разные типы.** Ожидаемый вложенный литерал массива в `results_eq` разворачивался как `text`, а фактическая колонка имеет `text[]`. Ожидание заменено запросом `SELECT ARRAY[...]::text[]`: проверяется то же точное содержимое массива. Добавлены три отказа загрузки: отсутствующий договор, чужой каталог, существующий чужой договор из своей папки.

Рабочий сценарий имеет 43 сохранённых контрольных точки и отдельную итоговую проверку 13 инвариантов. 125 SQL-проверок основного арендного сценария прошли в транзакции с откатом искусственных данных; все 144 модульных теста, TypeScript и ESLint новых скриптов/тестов прошли. Независимое ревью миграции и тестов не нашло блокеров после усиления проверки чужого договора. Советник Supabase не вернул ошибок; остаются предупреждения о намеренно доступных авторизованным пользователям RPC `SECURITY DEFINER` и выключенной проверке скомпрометированных паролей. Это не полный аудит безопасности.

Подготовка изолированных аккаунтов, одноразовый вход и API-сценарий описаны в [acceptance-runbook.md](acceptance-runbook.md).

Сквозные сценарии с записью данных и другими ролями проверялись локально в Chrome с перехватом Auth/REST/Storage. ## Исправленные проблемы

1. **Недоступные данные выглядели как нормальная сводка.** Кабинет мог показывать «Всё в порядке» и нулевые показатели после ошибки запросов. Теперь готовность каждого показателя определяется его источником; до загрузки показывается загрузка, при ошибке — недоступность. Ошибка истории поступлений не заменяется суммой из начислений. Совместимость с явно отсутствующим старым API истории сохранена.
2. **Неподходящий объект в форме ремонта.** В смешанном портфеле первый объект мог быть доступен только наблюдателю. Теперь создание учитывает права на выбранный объект, а начальный объект формы выбирается из доступных для записи.
3. **Контакты кандидата нельзя было очистить.** Пустое значение заменялось данными профиля. Теперь незаполненное пользователем состояние отличается от явно очищенного; в заявку передаются исправленные значения.
4. **Устаревшая ссылка на коммунальные услуги выбирала другой договор.** Теперь явно запрошенный недоступный договор не подменяется. Пользователь видит объяснение и может самостоятельно перейти к выбору другого договора.

До исправления шесть новых регрессионных сценариев и проверка коммунальной ссылки падали на исходной реализации. После исправления они проходят; прежние проверки сохранены. Независимое ревью пяти изменённых файлов интерфейса не нашло блокирующих замечаний. SQL, схемы и правила доступа не менялись; новые миграции для этих исправлений не нужны.

## Результаты проверок

- Исходный общий прогон: 39 браузерных сценариев по 12 файлам, 38 прошли; один остановился по таймауту `page.goto` страницы Telegram до выполнения проверок интерфейса.
- После исправления: все 16 сценариев по затронутым разделам прошли, включая шесть новых регрессий, проверку коммунальной ссылки и повтор Telegram. Всего в двух прогонах подтверждены 45 уникальных сценариев.
- 130 модульных тестов, TypeScript, ESLint изменённых файлов и production-сборка прошли.
- Проверки выполнялись во временной копии исходников с зависимостями по существующему lock-файлу. Рабочие зависимости и lock-файл не менялись. Браузерные проверки регистрации, требующие настоящего локального Supabase, не запускались.

## Границы приёмки и следующий этап

Основная цепочка подтверждена на рабочей базе под тремя ролями. Это сочетание настоящих API-операций и выбранных действий в опубликованном браузере; весь путь не воспроизводился исключительно кликами. Локальные браузерные регрессии дополняют эту проверку. Проверка не подтверждает каждую комбинацию устройств, ролей, конкурирующих изменений и ошибок провайдеров.

Для записи демонстрации следует подготовить короткий сценарий и отдельный наглядный набор данных: технический архив приёмки содержит длинные явные тестовые пометки. После коммита новой миграции повторно применять её в этом проекте не нужно — запись уже есть в истории Supabase. Другим окружениям миграция нужна.

Email пока имеет только шаблон, банковский приём платежей ещё не подключён. Они относятся к отдельным следующим этапам, а не к исправлениям этой проверки.
