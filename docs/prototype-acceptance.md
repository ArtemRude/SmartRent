# Проверка прототипа SmartRent

Дата: 27 октября 2026 года. Первый этап подготовки к демонстрации и пилоту.

## Что проверено

На опубликованном сайте проверен вход собственника и чтение существующих данных. Изменения договоров, платежей, доступов и публикаций не выполнялись. Сквозные сценарии с записью данных и другими ролями проверялись локально в Chrome с перехватом Auth/REST/Storage. Это проверка интерфейса и его API-контрактов, а не повторная проверка RLS или всей рабочей базы.

| Блок | Опубликованный сайт | Локальный браузер |
| --- | --- | --- |
| Вход и кабинет | Вход собственника, сводка и навигация | Подготовка первой аренды, загрузка и ошибки показателей |
| Объекты | Переход из финансов к объекту, карточка и страница команды | Каталог, фильтры, помещения, изменение, архивирование, отзыв доступа |
| Договоры | Существующий активный договор и связанные действия | Подготовка подписания, подтверждение текущей версии, активация |
| Заселение и выезд | Договор → выезд → форма осмотра; закрыта без сохранения | Собственник/администратор, арендатор, согласование версий и депозит |
| Продление | Правильный договор и действие предложения условий | Предложение, отказ, новая версия, подтверждение и отчёт |
| Платежи и расходы | Начисления, задолженность, финансовый отчёт | Учёт расходов, история исправлений, CSV и запрет финансов арендатору |
| Коммунальные | Выбранный договор, доступные действия, пустое состояние услуг | Показания, проверка, оплата; устаревшая ссылка для обеих ролей |
| Команда | Участники, выбранный объект, ответственное лицо и журнал | Приглашение, принятие, работа управляющего, отзыв доступа |
| Ремонты | Переход из объекта и выбранный фильтр, пустое состояние работ | Смета, согласование, отчёт, приёмка, расход; смешанные manager/viewer |
| Поиск арендаторов | Публичный каталог и вкладка публикаций объекта; карточек нет | Публикация, вход кандидата, отклик, показ и выбор собственником |
| Уведомления | Подключение Telegram и история принятых сообщений | Подключение, темы, ошибки, история и экран 320 px |
| Тарифы | Ранний доступ в кабинете | Проба, льгота, ограничения, роли и явный запуск администратором |

## Исправленные проблемы

1. **Недоступные данные выглядели как нормальная сводка.** Кабинет мог показывать «Всё в порядке» и нулевые показатели после ошибки запросов. Теперь готовность каждого показателя определяется его источником; до загрузки показывается загрузка, при ошибке — недоступность. Ошибка истории поступлений не заменяется суммой из начислений. Совместимость с явно отсутствующим старым API истории сохранена.
2. **Неподходящий объект в форме ремонта.** В смешанном портфеле первый объект мог быть доступен только наблюдателю. Теперь создание учитывает права на выбранный объект, а начальный объект формы выбирается из доступных для записи.
3. **Контакты кандидата нельзя было очистить.** Пустое значение заменялось данными профиля. Теперь незаполненное пользователем состояние отличается от явно очищенного; в заявку передаются исправленные значения.
4. **Устаревшая ссылка на коммунальные услуги выбирала другой договор.** Теперь явно запрошенный недоступный договор не подменяется. Пользователь видит объяснение и может самостоятельно перейти к выбору другого договора.

До исправления шесть новых регрессионных сценариев и проверка коммунальной ссылки падали на исходной реализации. После исправления они проходят; прежние проверки сохранены. Независимое ревью пяти изменённых файлов интерфейса не нашло блокирующих замечаний. SQL, схемы и правила доступа не менялись; новые миграции для этих исправлений не нужны.

## Результаты проверок

- Исходный общий прогон: 39 браузерных сценариев по 12 файлам, 38 прошли; один остановился по таймауту `page.goto` страницы Telegram до выполнения проверок интерфейса.
- После исправления: все 16 сценариев по затронутым разделам прошли, включая шесть новых регрессий, проверку коммунальной ссылки и повтор Telegram. Всего в двух прогонах подтверждены 45 уникальных сценариев.
- 130 модульных тестов, TypeScript, ESLint изменённых файлов и production-сборка прошли.
- Проверки выполнялись во временной копии исходников с зависимостями по существующему lock-файлу. Рабочие зависимости и lock-файл не менялись. Браузерные проверки регистрации, требующие настоящего локального Supabase, не запускались.

## Что нужно перед окончательной приёмкой

1. Закоммитить исправления, отправить их и опубликовать актуальную версию. На момент проверки опубликованный раздел «Уведомления» ещё использовал предыдущее оформление, хотя новое уже находится в коммите `b75922f`.
2. Повторить исправленные сценарии после публикации. Живые сессии арендатора и управляющего в этой проверке не использовались; их операции записи подтверждены локальными сценариями.
3. Подготовить отдельные демонстрационные данные для записи. В проверенном портфеле нет публичных карточек, ремонтов, расходов и настроенных коммунальных услуг; это допустимые пустые состояния, но они не показывают весь сценарий проекта.
4. Провести полный сценарий на явно выделенных тестовых данных опубликованного окружения, включая запись и согласование с арендатором, без изменения действующей аренды. До этого этапа полная приёмка рабочего окружения не считается закрытой.

Email пока имеет только шаблон, банковский приём платежей ещё не подключён. Они относятся к отдельным следующим этапам, а не к исправлениям этой проверки.
