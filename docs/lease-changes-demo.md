# Продление аренды и изменение условий

Третий пункт [плана развития](./product-roadmap.md). В разделе **«Изменения условий»** собственник или администратор предлагает ставку с будущего месяца и при необходимости продление срока. Арендатор подтверждает или отклоняет предложение в своём кабинете.

## Перед публикацией

Примените `20261020212449_lease_amendments_and_scheduled_rent.sql`, затем опубликуйте frontend. Миграция добавляет `lease_amendments`, `lease_amendment_events`, RPC сохранения/действий, проверки прав, защиту согласованных условий и расчёт будущих начислений по согласованным ставкам. Исходное поле ставки договора остаётся базой первоначального договора; будущие ставки берутся из принятой истории.

Проверка наличия объектов в Supabase SQL Editor:

```sql
select
  to_regclass('public.lease_amendments') is not null as proposals,
  to_regclass('public.lease_amendment_events') is not null as history,
  to_regprocedure('public.save_lease_amendment(uuid,jsonb,uuid,integer)') is not null as save_function,
  to_regprocedure('public.act_on_lease_amendment(uuid,text,integer,text)') is not null as actions_function;
```

Все значения должны быть `true`. Это проверяет наличие объектов, а не выполнение всего процесса. Из локальной сессии миграция к рабочему проекту не применялась.

## Сценарий записи

Подготовьте активный договор со ставкой **60 000 ₽**, связанным кабинетом арендатора и окончанием аренды через несколько месяцев. Для демонстрации изменения ставки используйте будущие месяцы без внесённых оплат и ожидающих проверки сообщений об оплате.

1. В карточке договора нажмите **«Продлить / изменить условия»**, затем **«Предложить новые условия»**.
2. Укажите **65 000,25 ₽** с первого числа следующего месяца, продлите дату окончания и добавьте комментарий. Сохраните предложение. Это черновик: арендатор его не видит, срок и начисления не меняются.
3. Отправьте предложение арендатору. Покажите второй профиль браузера: в кабинете арендатора есть **«Изменения условий»** и уведомление.
4. Арендатор отклоняет предложение с причиной «Предлагаю меньшую ставку». Собственник видит отказ и готовит новое предложение **64 000,10 ₽**. Отклонённая версия остаётся в истории.
5. Отправьте новое предложение. Арендатор подтверждает его. Срок действующего договора продлевается, в график добавляются новые месяцы. С первого числа выбранного месяца база аренды становится **64 000,10 ₽**. Текущий и прошлые месяцы сохраняют прежние суммы.
6. Покажите ставку в карточке договора и кабинете арендатора: до даты изменения там по-прежнему **60 000 ₽**. План платежей и прогноз уже учитывают будущую ставку по соответствующим месяцам.
7. Откройте **«Соглашение / PDF»**. В печатной форме есть сохранённые стороны, объект, ставка до/после, дата её начала, прежний и новый срок, комментарий и отметка подтверждения арендатора. В истории можно открыть печатную форму конкретной версии.
8. Вернитесь к первоначальному договору: подписанный PDF сохранён, сгенерированный предпросмотр использует исходные ставку и дату окончания. Ручное изменение закреплённых условий заблокировано; следующие изменения оформляются новым предложением.

Администратор проходит тот же сценарий по договору другого собственника, но не может подтвердить условия за арендатора. Автор каждого действия сохраняется в базе.

## Правила работы

- Ставка меняется с **первого числа будущего месяца**. Подтверждение возможно до этой даты включительно; задним числом условия не применяются. Если дата прошла, отмените предложение и создайте новое.
- В одном договоре одновременно может быть один черновик или ожидающее предложение. Согласованная версия неизменяема. Следующая дата ставки должна быть позже предыдущей согласованной даты; можно заранее согласовать несколько последовательных ступеней.
- Продление допускается для активного договора, без сокращения текущего срока. Новая дата должна включать месяц изменения. Горизонт нового продления — до пяти лет от текущей даты; уже существующий более длинный срок не сокращается.
- Согласованное продление сразу расширяет график действующего договора. Ставка применяется только с указанного месяца. Ночной запуск или открытая вкладка для смены ставки не нужны: ставки определяются по истории для каждого расчётного месяца.
- Если затронутый месяц уже оплачен полностью/частично или есть сообщение об оплате на проверке, изменение его базы блокируется. Разберитесь с оплатой или выберите более поздний месяц. Автоматического возврата, переноса денег или удаления платежей нет.
- Продление без изменения ставки может сохранить предоплату. При пересчёте сохраняются ручные корректировки начислений; отрицательный итог после снижения ставки блокируется.
- Неполный месяц, день оплаты, коммунальные тарифы, депозит и остальные положения этим модулем не меняются. Для них сохраняются существующие сценарии. Новое предложение содержит ставку, дату начала, срок и пояснение.
- Перед завершением аренды ожидающее предложение нужно согласовать либо отменить. Завершение после согласования сохраняет историю, текущий и прошлый долг, а также оплаченные будущие периоды по существующим правилам выезда.
- После завершения аренды можно открыть историю изменений, а в договорах — **«Новый договор»**, чтобы создать отдельный черновик с новым номером и документами.
- Подтверждение в кабинете фиксирует согласование условий. Оно не означает загрузку подписанного PDF, квалифицированную электронную подпись или совершение оплаты. Печатное соглашение можно сохранить в PDF и подписать отдельно.

## Проверки

- Unit-тесты: выбор ставки по месяцу, последовательные ступени, сохранение исходного срока, прогноз, точность копеек в печатной форме и защита от вставки HTML.
- `lease_amendments_workflow_test.sql`: RLS для owner/admin/tenant/anon, скрытие черновиков, роли из базы вместо metadata, версии, отказ и повторное предложение, блокировка оплаченных периодов и ожидающих сообщений, сохранение базы и прошлого долга, расширение графика, повторное подтверждение, несколько будущих ставок, продление с предоплатой и последующий выезд.
- SQL проверен в изолированной PostgreSQL через PGlite с адаптером Auth/Storage/pgTAP. Полные проверки Supabase/Docker и advisors остаются частью CI/деплоя.
- Браузерные проверки `e2e/lease-changes.spec.ts` используют перехваченные локальные Auth/REST и не меняют рабочую базу. Проверяют путь из договоров и кабинета арендатора, отказ, повторное предложение, ошибку при оплате, согласование, исходный документ, печатный PDF, мобильную ширину и отсутствие новой схемы. Один и тот же сценарий выполняется для собственника и администратора.
