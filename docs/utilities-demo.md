# Демонстрация коммунальных платежей

Модуль находится в разделе **«Коммунальные услуги»**. Из договора собственника и кабинета арендатора доступны прямые переходы к нужному договору.

## Подготовка

Перед демонстрацией опубликуйте frontend и примените миграцию `20261014145946_utility_meters_and_billing.sql` штатным механизмом деплоя проекта. Миграция добавляет таблицы, RPC, права доступа и приватный bucket фотографий. Без неё раздел показывает сообщение о временной недоступности.

Для записи нужны аккаунты собственника и связанного арендатора, объект и активный договор с текущей датой внутри срока аренды. Используйте вымышленные контакты и документы в отдельном тестовом окружении.

## Сценарий на 2–3 минуты

1. Собственник выбирает договор, открывает **«Счётчики и услуги»** и добавляет **«Холодная вода»**: единица **м³**, тариф **42,75 ₽**, начальные показания **100**, первый расчётный месяц — текущий.
2. Собственник добавляет фиксированную услугу **«Интернет»**: **500 ₽ в месяц**.
3. Арендатор открывает **«Показания и расчёты»**, вводит **103,2** и при необходимости прикладывает фотографию счётчика.
4. На экране виден расчёт: **3,2 м³ × 42,75 ₽ = 136,80 ₽**, интернет **500 ₽**, итого **636,80 ₽**. Аренда начисляется отдельно.
5. Арендатор отправляет расчёт на проверку. Собственник открывает уведомление, проверяет показания и утверждает сумму со сроком оплаты.
6. В разделе **«Платежи»** появляются отдельные начисления **«Аренда»** и **«Коммунальные услуги»**. Ссылка из коммунального начисления открывает его расшифровку.
7. Арендатор сообщает об оплате через свой кабинет; собственник подтверждает её существующим механизмом платежей.

Для демонстрации исправления собственник сначала возвращает расчёт с причиной, затем арендатор отправляет показания повторно. Оба варианта сохраняются в истории.

Повторное утверждение не создаёт второй долг. После утверждения месяца повторная отправка за этот или более ранний месяц запрещена. Для повторной записи используйте новый тестовый договор.

## Проверки

- `npm run verify` — бизнес-логика, TypeScript, ESLint и сборка.
- `supabase start`, затем `npm run test:db` — pgTAP/RLS, включая `utility_workflow_test.sql`.
- `npm run test:e2e:local` — браузерные проверки в локальном окружении.

UI-сценарий `e2e/utilities.spec.ts` перехватывает Auth, REST и Storage и не меняет данные Supabase. Его можно запустить отдельно без работающего API:

```sh
E2E_SUPABASE_URL=http://127.0.0.1:54321 \
E2E_SUPABASE_PUBLISHABLE_KEY=fixture \
npx playwright test e2e/utilities.spec.ts
```

В текущей сессии SQL проверен в изолированной PostgreSQL через PGlite с адаптером окружения Auth/Storage и SQL-проверками, соответствующими pgTAP-утверждениям. Проверка через настоящий локальный Supabase/Docker и применение к рабочей базе остаются отдельными шагами перед публикацией.
