# Команда управляющих

Четвёртый пункт [плана развития](./product-roadmap.md). В разделе **«Команда»** собственник приглашает помощников, выдаёт доступ к выбранным объектам и назначает ответственного. Сотрудник работает с объектами в этом же разделе, сохраняя свою личную роль собственника или арендатора.

## Перед публикацией

Примените `20261021115654_property_team_workspace.sql`, затем опубликуйте frontend. Миграция добавляет участников, доступы по объектам, ответственных, журнал и семь RPC. Существующие роли приложения, финансовые операции и доступ к документам не расширяются.

Проверка наличия схемы в Supabase SQL Editor:

```sql
select
  to_regclass('public.team_memberships') is not null as members,
  to_regclass('public.team_property_access') is not null as property_access,
  to_regclass('public.team_property_responsibles') is not null as responsible,
  to_regclass('public.team_activity') is not null as activity,
  to_regprocedure('public.team_overview()') is not null as overview,
  to_regprocedure('public.team_workspace(uuid)') is not null as workspace;
```

Все значения должны быть `true`. Это проверяет наличие объектов, а не весь сценарий. Миграция из этой локальной сессии к рабочему проекту не применялась.

## Сценарий записи

Подготовьте два объекта собственника и заявку арендатора на одном из них. Для сотрудника используйте отдельный аккаунт с подтверждённым email и второй профиль браузера.

1. Откройте **«Команда» → «Пригласить»**. Укажите email сотрудника, роль **«Управляющий»** и только первый объект. Второй оставьте без доступа.
2. Сохраните приглашение. Скопируйте ссылку из диалога и передайте её сотруднику самостоятельно. Письмо автоматически не отправляется. Ссылка действует семь дней и показывается после создания; повторное приглашение на ожидающий email заменяет прежнюю ссылку.
3. Во втором профиле откройте ссылку, войдите или зарегистрируйтесь с приглашённым email и подтвердите email. После входа нажмите **«Принять приглашение»**. При открытии письма подтверждения в другом браузере повторно откройте исходную ссылку приглашения в этом браузере.
4. Покажите, что сотруднику доступен только выбранный объект: помещения, краткие условия аренды, заявки, обсуждение и заметки. Другой объект, документы, паспортные данные и финансовые операции ему не выдаются.
5. Собственник назначает сотрудника **ответственным по объекту**. Во втором профиле отметка обновляется автоматически.
6. Сотрудник сохраняет заметку, переводит заявку **«В работу»** и добавляет комментарий. Собственник видит автора и действия в журнале команды. Та же заявка и комментарий доступны собственнику и арендатору в обычном разделе заявок; статус сохраняется в прежней истории.
7. Собственник меняет роль на **«Наблюдатель»**. Сведения и обсуждение остаются видны, кнопки записи исчезают. Назначение ответственным снимается: для него нужна роль управляющего.
8. Нажмите **«Отозвать доступ»**. Открытая вкладка сотрудника убирает сведения объекта после обновления доступа; новые запросы к базе сразу отклоняются. История действий и ранее оставленные комментарии сохраняются.

## Границы ролей

| Возможность                                                                        | Собственник           | Управляющий               | Наблюдатель               |
| ---------------------------------------------------------------------------------- | --------------------- | ------------------------- | ------------------------- |
| Выбранные объекты, помещения, краткие условия аренды, заявки, обсуждение и заметки | Свои объекты          | Выданные объекты          | Выданные объекты          |
| Статусы заявок, комментарии и заметки по объекту                                   | Да                    | Да                        | Только просмотр           |
| Приглашения, роли, объекты доступа, ответственные и журнал всей команды            | Да                    | Нет                       | Нет                       |
| Изменение договора, платежей, расходов, заселения и выезда, файлы документов       | Через прежние разделы | Не выдаётся ролью команды | Не выдаётся ролью команды |

Назначение ответственным — отметка координации, оно само по себе не выдаёт права. Их определяют роль и список объектов. Глобальный администратор не может управлять чужой командой через командные RPC; его прежние административные права приложения сохраняются.

## Проверки и ограничения

- Секрет приглашения находится во фрагменте ссылки, который не передаётся веб-серверу; до входа сохраняется в sessionStorage текущей вкладки. В базе хранится только SHA-256 хеш. Списки участников и журнал секрет не возвращают.
- Принятие требует совпадения с подтверждённым `auth.users.email`. Редактируемый профиль, metadata и личная роль не подтверждают приглашённый email.
- Каждая операция проверяет актуальное членство, роль и собственника объекта в базе. Изменение прав и командные записи сериализуются; устаревшие версии доступа и статуса заявки отклоняются. Права не берутся из кешированного JWT.
- Таблицы команды закрыты для прямого доступа браузера; чтение и запись проходят через ограниченные RPC. Прежние политики владельца, арендатора и Storage не расширяются. Сотрудник не может напрямую удалить свои командные комментарии после отзыва доступа.
- Интерфейс показывает последние 100 событий команды, 200 заявок на объект, 500 комментариев к показанным заявкам и 50 заметок. При усечении есть явная подпись. Полная история сохраняется в базе.
- Вкладка обновляется каждые пять секунд. При ошибке доступа старые сведения скрываются. Серверный отзыв действует сразу для следующих операций; уже прочитанные человеком сведения отозвать невозможно.
- `team_workflow_test.sql` проверен вместе с прежними SQL-сценариями в изолированном PostgreSQL через PGlite и адаптер Auth/Storage/pgTAP. Полный Supabase/Docker здесь не запущен: `supabase db advisors --local` не подключился к локальному Postgres. Нативные проверки и advisors остаются частью CI/деплоя.
- Браузерные проверки `e2e/team.spec.ts` используют локальные перехваченные Auth/REST: приглашение через вход, обе личные роли, работа с заявкой, режим просмотра, отзыв, устаревшая запись, ошибка доступа, другой email, отсутствующий RPC и мобильная ширина. Рабочая база не меняется.
