# Изолированная приёмка опубликованного прототипа

Скрипты предназначены для оператора проекта `euuyvfidarhpeqeeheuu`. По умолчанию они показывают план и ничего не меняют. Не использовать рабочие аккаунты как тестовые и не подменять JWT через SQL или localStorage браузера.

## Подготовка

Нужен Node.js 22+ и установленные зависимости проекта. В защищённом окружении процесса задаются `ACCEPTANCE_SUPABASE_URL=https://euuyvfidarhpeqeeheuu.supabase.co`, `ACCEPTANCE_PUBLIC_KEY` и `ACCEPTANCE_SERVICE_KEY`. Служебный ключ нужен только для создания новых фиктивных пользователей; не передавать его в браузер, командную строку или коммит.

```sh
node scripts/acceptance-live.mjs --plan
node scripts/acceptance-live.mjs --setup
```

`--setup` создаёт три новых подтверждённых аккаунта `acceptance-<UUID>-<role>@example.invalid`, один объект и приглашение управляющего только к этому объекту. Письма не отправляются, Telegram не подключается. Сценарий останавливается, если платный запуск уже включён; не следует обходить это ограничение изменением общих настроек биллинга.

Результат содержит `state_dir=/tmp/smartrent-acceptance-<UUID>`. Каталог имеет права `0700`, файлы `0600`. `manifest.json` содержит область теста и контрольные точки. `*-session.json` и `browser-links.json` содержат секреты; их нельзя выводить, отправлять, прикладывать к отчёту или копировать в репозиторий. Не повторять `--setup` ради продолжения: это создаёт новый независимый набор данных. После подготовки убрать служебный ключ из окружения процесса.

Supabase Auth должен возвращать пользователя в опубликованное приложение: Site URL `https://mysmartrent.lovable.app`, разрешённые адреса `/dashboard` и `/cabinet` на том же origin. Скрипт сам не меняет конфигурацию Auth; если `browser_links_ready=false`, сначала устранить причину и выпустить новые ссылки только для созданных тестовых аккаунтов. Не добавлять произвольные wildcard-адреса.

## Проверка интерфейса

```sh
node scripts/acceptance-browser.mjs --serve /tmp/smartrent-acceptance-<UUID>
```

Открыть выведенный локальный URL. Ссылки одноразовые: они перенаправляют на штатный Supabase Auth, а не вставляют сессию в приложение. Сервер доступен только на `127.0.0.1`, проверяет Host и origin навигации, не выводит токены и закрывается через час. Остановить его после проверки. Все вкладки приложения в одном браузере используют общую сессию — при смене роли полностью переходить по новой ссылке и проверять имя аккаунта.

Собственник проверяет свой тестовый объект и заметки команды; арендатор — отклик, свой договор, показания, заявки и уведомления; управляющий — только назначенный объект, кандидатов, заявки и сметы. Реальные объекты и финансы не изменять. Отдельно проверять отказ запрещённого действия, а не только отсутствие кнопки.

## Сквозной сценарий API

Это программный модуль, для запуска которого требуется операторская обвязка загрузки сессий и сохранения контрольных точек. Готовая CLI-команда полного сценария в репозитории пока не предусмотрена. Модуль `scripts/acceptance/rental-workflow.mjs` экспортирует `runRentalWorkflow({clients, state, saveState, allowPublicListing, report})`:

- `state` — манифест именно этого запуска; `clients` — три разных Supabase-клиента со своим пользовательским JWT, восстановленным из соответствующего приватного файла. Ключ клиента только публичный, не `service_role`.
- `saveState` атомарно сохраняет тот же изменяемый объект `state` в приватный манифест **до** и после операции. `report` получает безопасные поля этапа и результата, без провайдерских ответов и токенов.
- Без `allowPublicListing: true` создаются только черновик карточки и тестовое фото. Полный режим временно публикует явно вымышленное объявление; включать его осознанно для согласованной приёмки.
- Полный режим проходит отбор, договор с тестовым PDF, заселение, учётную частичную оплату, ремонт, будущую ставку и выезд; создаёт один неоплаченный расход, закрывает карточку и архивирует объект. Денежных переводов нет.
- Контрольная точка `done` переиспользуется; `pending`/`uncertain` требует сверки с фактическими данными. Не удалять её и не повторять запись, пока не доказано, что она не сохранилась. Сохранённое значение не заменяет итоговую проверку состояния базы.
- При ошибке модуль пытается снять с публикации только проверенную тестовую карточку. Не завершает действующий договор и не архивирует объект автоматически после ошибки. Если результат скрытия неизвестен, нужна ручная сверка.

Операторский вызывающий код должен проверить права приватных файлов, загрузить `state`, восстановить три сессии через `auth.setSession`, передать функцию атомарного сохранения с `0600` и вызвать модуль. Служебный ключ этому коду не нужен. Интерфейсные операции выполняются отдельно: результат `browser_acceptance: pending` намеренно не превращается в успешную браузерную приёмку только из-за завершения API-сценария.

В приёмке 29.10 интерфейсный оператор создавал отклик, заявку и смету, затем сверял их по объекту, роли, точной метке запуска и единственности результата перед продолжением API. Это не автоматизация браузера, встроенная в модуль.

## Завершение

Повторно прочитать конечные состояния через реальные роли: договор завершён, акты подтверждены, заявка закрыта, ремонт принят, расход единственный и неоплаченный, частичная оплата не продублирована, карточка непублична, объект архивирован. Проверить недоступность закрытых финансов и посторонних объектов управляющему. Сохранить отчёт без секретов; завершить тестовые сессии и локальный сервер. Историю теста не удалять каскадно и не менять реальные записи для «очистки».

Проверки кода:

```sh
node --experimental-strip-types --test tests/*.test.ts
supabase test db
```

SQL-тесты создают искусственные записи внутри транзакции и откатывают их. В тесте фотографий сравнивается колонка `text[]` с результатом `SELECT ARRAY[...]::text[]`; вложенный литерал в перегрузке `results_eq` не эквивалентен такому сравнению.
